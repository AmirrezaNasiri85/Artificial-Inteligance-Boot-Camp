A Quick Distinction, Restated

What Feature Engineering Actually Is

Turning raw columns into columns a model can actually learn from -- fixing gaps, reshaping distributions, encoding categories as numbers, and combining columns into new ones that carry signal none of the originals expressed alone.

LectureQuestion it answers
Feature Selection (03)"Of the columns I have, which deserve to stay?"
Feature Engineering (today)"What new columns would actually help, and how do I build them correctly?"

A realistic order: engineer new candidate features first (today), select among the enlarged set afterward (Lecture 03's tools), then validate the result honestly (Lecture 04's tools). All three lectures are one pipeline, not three separate topics.

Often the Biggest Lever You Have

"Data quality beats algorithm choice" was stated as a principle in Lecture 01. Feature engineering is where that principle turns into concrete work: a well-built feature can help a simple model more than switching to a fancier algorithm ever would.

A useful gut check before reaching for a more complex model: is there a feature -- a ratio, a date part, a combination of two columns -- that would let an existing simple model see the pattern directly, instead of needing a more powerful model to infer it indirectly from raw columns?

The Most Common Real-World Problem

Handling Missing Values: Imputation

Most models can't handle a blank cell directly -- something has to fill it in. The choice of what to fill in with is itself a feature engineering decision.

StrategyGood forWatch out for
MeanRoughly symmetric numeric columnsPulled around by outliers, same as the mean itself
MedianSkewed numeric columns (income, price)Ignores the shape beyond the midpoint
ModeCategorical columnsCan over-represent an already-common category
Constant (e.g. "Unknown")When "missing" itself might be meaningfulAdds a new category a model must still learn about

SimpleImputer(strategy=...) handles all four -- and, like every data-dependent step, its fitted fill values must come from the training fold only (Lecture 04's rule, applying here too).

In [ 6 ]:
A Detail Worth Not Throwing Away

Sometimes "Missing" Is the Signal

Imputing a value quietly erases the fact that it was ever missing -- but sometimes whether a value was recorded at all is informative in its own right. A skipped income field, a never-completed survey question, a sensor that failed to report -- these can correlate with the outcome you're predicting.

SimpleImputer(add_indicator=True) keeps both: the filled-in value, and a new 0/1 column recording where a value was originally missing. The model gets to use whichever one (or both) turns out to matter.

A Quick Recap, With One New Idea

Scaling: Which Models Actually Need It

StandardScaler has appeared in nearly every notebook so far -- worth being explicit about why, and which models it doesn't matter for.

Scaling matters a lot

Linear/Logistic Regression, SVM, KNN, anything using gradient descent, anything measuring distance -- all directly affected by features being on wildly different scales (e.g. age in years vs. income in dollars).

Scaling barely matters

Decision Trees and tree ensembles (Random Forest, Gradient Boosting) split on thresholds one feature at a time -- whether a feature is measured in dollars or thousands of dollars doesn't change where a good split falls.

Default habit that's rarely wrong: scale numeric features whenever you're not certain the model is tree-based. It essentially never hurts a linear or distance-based model, and unnecessary scaling doesn't damage a tree-based one either.

In [ 8 ]:
Reshaping a Distribution

Log and Power Transforms for Skewed Data

Income, prices, population, transaction amounts -- real-world numeric columns are very often right-skewed: a long tail of large values pulling the mean away from where most of the data actually sits. Many models (especially linear ones) work better when that skew is reduced.

log(x) compresses large values much more than small ones -- turning a long right tail into something closer to symmetric. PowerTransformer (Box-Cox / Yeo-Johnson) finds a more general transform automatically, including handling zero or negative values Box-Cox can't.

A quick way to check if it helped: plot a histogram before and after -- if the transformed version looks noticeably more symmetric and bell-shaped, it was probably worth doing.

In [ 9 ]:
Turning a Number Into a Category

Binning / Discretization

Sometimes a continuous number matters less than which range it falls into -- age as "child / adult / senior" instead of an exact year count, or income as quartiles instead of a raw dollar figure.

When it helps

The true relationship is a step function, not smooth (a discount kicking in exactly at "age 65"); or you want a simpler, more interpretable feature for a stakeholder-facing model.

The cost

Information is genuinely thrown away -- two ages in the same bin become indistinguishable to the model, even if they mattered differently before binning.

KBinsDiscretizer(n_bins=..., strategy=...) handles this -- strategy='quantile' gives every bin roughly equal counts; strategy='uniform' gives every bin equal-width ranges.

A Recap, Made Explicit

Categorical Encoding: One-Hot vs. Ordinal

OneHotEncoder has appeared constantly so far, always for the same kind of column: categories with no natural order (neighborhood, payment method). A different kind of column needs a different encoder.

One-HotOrdinal
Use whenCategories have no inherent orderCategories DO have a natural order
ExampleNeighborhood, payment methodEducation level, shirt size, satisfaction rating
OutputOne 0/1 column per categoryA single column of integers (0, 1, 2, …)
Risk if used wrongWastes columns on ordered dataInvents a false distance between unordered categories

The test: would it be reasonable to say category B is "between" A and C? If yes, ordinal fits. If the categories could be listed in any order without losing meaning, one-hot is correct.

In [ 11 ]:
When One-Hot Stops Working Well

High-Cardinality Categories & Target Encoding

A column like zip_code or product_id might have thousands of distinct values -- one-hot encoding it explodes the feature count into thousands of mostly-empty columns.

Target encoding (a.k.a. mean encoding) replaces each category with the average target value for that category in the training data -- "this zip code's average churn rate is 31%" becomes a single number, not thousands of columns.

The catch, and it's a real one: target encoding computes a statistic using the target column itself -- which makes it unusually easy to leak test information into training if you're not careful about exactly which rows' target values go into each category's average. The notebook makes this concrete.

A Column Type Models Can't Use Directly

Date & Time Features

A raw timestamp is nearly useless to most models as-is -- but the calendar fields hiding inside it (already used in the Pandas advanced-topics notebook via .dt) are often some of the most predictive features available.

Common extractions

Year, month, day, day-of-week, hour, is-weekend, days-since-a-reference-date (exactly what the churn capstone's tenure_months was).

Why they help

Sales spike on weekends; support tickets cluster on Mondays; churn risk changes with tenure -- patterns tied to calendar structure that a raw timestamp hides completely.

In [ 13 ]:
A Subtle Trap in Date Features

Cyclical Encoding: December and January Are Neighbors

Month as a plain number (1-12) tells a model that December (12) is as far from January (1) as it's possible to get -- but on a real calendar, they're right next to each other. The same problem hits hour-of-day (23:00 and 00:00) and day-of-week.

The fix: encode the cyclical feature as two new columns, sin(2π · month / 12) and cos(2π · month / 12). Together, these two numbers place every month at its correct position on a circle -- December and January end up genuinely close together, the way they should be.

In [ 14 ]:
When Two Columns Together Say More

Interaction Features

Some effects only show up in combination. A discount code might only matter for first-time customers; square footage might only command a premium in certain neighborhoods. A linear model, on its own, cannot see this -- it only sees each feature's independent effect, added together.

area_sqft × neighborhood_Downtown -- a new column that's zero everywhere except Downtown rows, where it equals the area. A linear model can now give Downtown houses a different price-per-square-foot than everywhere else, something no combination of the two original features could express alone.

PolynomialFeatures(interaction_only=True) generates every pairwise product automatically -- useful for a first pass, though it grows fast with many features, same caution as Lecture 02's polynomial degree.

In [ 15 ]:
Comparing a Row to Its Group

Aggregation Features: Group Statistics as New Columns

Sometimes what matters isn't a row's raw value, but how it compares to others like it. Is this house expensive for its neighborhood, or just expensive overall? Is this customer's usage high for their plan type, or high in general?

price_vs_neighborhood_avg = price / mean(price, grouped by neighborhood) -- a groupby().transform() away in Pandas. This kind of relative feature often carries more signal than either the raw value or the group average alone.

A leakage risk hides here too: the group average must be computed from training rows only -- computing it from the full dataset lets test rows quietly influence the very statistic used to describe them. Same rule as target encoding, same fix.

A Sneakier Version of an Old Problem

The Leakage Trap for Feature Engineering

Target encoding and aggregation features are especially easy to leak, because -- unlike scaling or imputing -- the feature itself is computed from the target, or from other rows' values. It's not always obvious you're touching data you shouldn't.

The leaky way

Compute each category's average target (or each group's average value) using every row, including rows that will later become the test set. Every row's engineered feature is partly built from its own target value.

The correct way

Compute the average using only the training fold, then apply that fitted mapping to the test fold. Inside cross-validation, this means recomputing the averages fresh, inside every single fold.

Exactly the same fix as always: put the encoder inside the Pipeline that gets cross-validated, so it's structurally impossible to compute it on the wrong rows. The notebook shows the inflated score this produces when skipped.

A Decision, Not an Automatic Step

Outliers: Detect, Then Decide

An unusually large or small value isn't automatically an error -- it might be the most important row in the dataset (the fraud case, the viral post). Detecting outliers is mechanical; deciding what to do about them is judgment.

DetectionHow it works
IQR methodFlag anything beyond 1.5x the interquartile range past Q1/Q3
Z-scoreFlag anything more than ~3 standard deviations from the mean

Cap / winsorize

Clip extreme values to a reasonable maximum instead of removing them -- keeps the row, softens its influence.

Remove

Justified when a value is a clear data-entry error (age = 200) -- risky when the "outlier" is a genuine, rare, important case.

Making It All Safe by Construction

Every Technique Today Belongs in the Pipeline

Imputers, scalers, encoders, custom transforms -- every one of today's techniques is data-dependent, and every one of them follows Lecture 04's rule: fit on training data only. ColumnTransformer and FunctionTransformer turn that rule into structure instead of memory.

Cross-validate or grid-search the whole pipeline, and every fold engineers, selects, and trains fresh -- using only that fold's training rows, at every single stage.
