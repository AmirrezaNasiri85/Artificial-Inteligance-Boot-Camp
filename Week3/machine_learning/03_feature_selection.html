Feature Selection

Not every column you have deserves a place in the model. This lecture is about deciding, deliberately, which features earn that place — and the one mistake in how you decide that quietly invalidates everything downstream.

Filter

Score features using statistics alone, before any model is trained

Wrapper

Try subsets of features against a real model and keep what performs best

Embedded

Selection happens as a side effect of training itself — Lasso, tree importances

Why Bother?

More Features Isn't Automatically Better

It's tempting to hand a model every column you have and let it "figure out" what matters. Four concrete reasons that instinct backfires.

Overfitting risk

More features means more ways to fit noise in the training set — the high-variance picture from Lecture 01, now driven by column count instead of polynomial degree.

The curse of dimensionality

As feature count grows, data points spread thin across an exponentially larger space — "nearby" stops meaning much, and models need exponentially more data to compensate.

Cost

Every extra feature is more data to collect, clean, store, and compute over — for production systems, at real scale, that's real money and real latency.

Interpretability

A model with 8 meaningful features is something you can explain to a stakeholder. A model with 200 features, most irrelevant, is a black box regardless of algorithm.

The Big Picture

Three Families of Methods

Every feature selection technique falls into one of three families, split by whether and how a model gets involved in making the decision.

FilterWrapperEmbedded
Uses a model?No — pure statisticsYes — trains many modelsYes — one model, selection built in
SpeedFastSlow (many training runs)As fast as training once
Considers feature interactions?No — one feature at a timeYesYes
ExamplesVariance threshold, correlation, ANOVA F-testRFE, forward/backward selectionLasso, tree importances

A common, sensible workflow uses more than one: a cheap filter pass to drop obviously useless columns first, then a wrapper or embedded method to fine-tune what remains — exactly the order this lecture builds in.

In [ 5 ]:
Filter Methods, Part 1

Variance Threshold: Remove What Barely Changes

The cheapest possible filter, and often the first pass on any new dataset: a feature that is (almost) the same value for every row carries almost no information — it can't help separate one row's outcome from another's, no matter how it correlates with anything else.

VarianceThreshold(threshold=0.0) drops any column with exactly one distinct value — a "sanity check" filter. A small positive threshold (after scaling) catches near-constant columns too.

Limitation to keep in mind: variance says nothing about the relationship to the target — a high-variance feature can still be completely irrelevant to y. It only catches the most obvious case: features with barely any variance at all.

In [ 6 ]:
Filter Methods, Part 2

Scoring Features Against the Target

The next filter step asks the real question: how strongly does each feature, alone, relate to y?

Regression targets

f_regression — an F-test measuring linear correlation between each feature and a continuous target, one feature at a time.

Classification targets

f_classif (ANOVA F-test) or mutual_info_classif — the latter also catches non-linear relationships a correlation coefficient would miss entirely.

SelectKBest(score_func, k=...) keeps only the top k scoring features — one line, applied after computing any of the scores above.

In [ 7 ]:
Filter Methods, Part 3

Redundancy: When Two Features Say the Same Thing

Scoring against the target catches irrelevant features. It does not catch two features that are both highly relevant — because they're both proxies for the same underlying signal. That's a job for correlation between features, not against the target — directly picking up where Lecture 02's VIF discussion left off.

Common rule of thumb: if two features correlate above ~0.9 with each other, keep the one that's cheaper to collect, more interpretable, or more complete (fewer missing values) — and drop the other. The information is barely lost.

In [ 8 ]:
Wrapper Methods, Part 1

Forward Selection vs. Backward Elimination

Filters score one feature at a time and never train a real model. Wrapper methods do the opposite: they repeatedly train the actual model on different feature subsets, and let real performance — not a proxy statistic — decide.

Forward Selection

Start with zero features. Repeatedly add whichever remaining feature improves performance the most — stop when no addition helps enough.

Backward Elimination

Start with all features. Repeatedly remove whichever one hurts performance the least — stop when every remaining feature matters.

The cost is real: testing every candidate at every step means training the model many times over — feasible for tens of features, painful for hundreds.

In [ 9 ]:
Wrapper Methods, Part 2

Recursive Feature Elimination (RFE)

A more efficient backward elimination: instead of testing every possible feature to drop at each step, RFE uses the model's own ranking (coefficients, or importance scores) to remove the weakest feature directly, then retrains — repeating until the target count is reached.

RFECV adds cross-validation on top: instead of you picking the target feature count, it tries several counts and keeps whichever performed best under cross-validation — a preview of Lecture 04.

In [ 10 ]:
Embedded Methods, Part 1

Lasso: Selection as a Side Effect of Fitting

Lecture 02 showed Lasso's L1 penalty driving polynomial coefficients to exactly zero. That's not a curiosity — it's a full feature selection method, with no separate selection step at all. Fit once, and the zero coefficients tell you which features were dropped.

SelectFromModel(Lasso(alpha=...)) formalizes this: fit the Lasso, then keep exactly the features whose coefficients survived above a threshold (zero, by default).

The knob that controls how aggressive this is: alpha. Larger alpha means a stronger penalty, which zeroes out more coefficients — pushing toward fewer, more conservative features.

In [ 11 ]:
Embedded Methods, Part 2

Tree-Based Feature Importance

Random Forest and Gradient Boosting track, for every split in every tree, how much that split reduced error — summed up per feature, this becomes .feature_importances_, exactly what the churn capstone plotted to sanity-check its model against the EDA.

SelectFromModel(RandomForestClassifier()) keeps whatever features scored above the mean importance by default — same idea as Lasso's threshold, different scoring mechanism underneath.

Bonus: tree importances naturally capture non-linear relationships and interactions between features — something the linear-model-based methods (Lasso, RFE with LinearRegression) structurally cannot see.

Putting It Together

Choosing a Method for the Situation

SituationReach for
Huge number of features, need a fast first passFilter (variance, correlation)
Suspect features overlap heavily with each otherFilter (correlation matrix / VIF)
Modest feature count, want the best possible subsetWrapper (RFE / RFECV)
Already fitting a linear model — get selection "for free"Embedded (Lasso)
Already fitting a tree ensemble — get selection "for free"Embedded (tree importances)
Suspect non-linear feature/target relationshipsFilter (mutual information) or Embedded (trees)

In practice: filter first to cut the obvious dead weight cheaply, then let whichever model you're training anyway (Lasso, a tree ensemble, or RFE) do the fine-grained work.

In [ 13 ]:
The Mistake That Invalidates Everything Else

Select Features Before or After the Split?

After. Always after — or more precisely, only ever using the training data, at every stage of every fold.

The leaky way

Score every feature against y using the entire dataset, keep the best ones, then split into train/test. The test set has already influenced which features were chosen — Lecture 01's "never grade your own homework" rule, broken quietly.

The correct way

Split first. Fit the feature selector on the training fold only, then apply that same fitted selection to the test fold. Inside cross-validation, this means re-selecting features fresh, inside every single fold.

Why this matters more than it sounds: with many features and few samples, selecting on the full dataset first can make even pure random noise look like a strong predictor — the notebook demonstrates this concretely, not just as a warning.

Don't Confuse the Three

Feature Selection vs. Feature Engineering vs. Dimensionality Reduction

TechniqueWhat it doesResult
Feature Selection (today)Chooses a subset of existing columnsFewer columns, each one still meaningful and interpretable on its own
Feature Engineering (Lecture 05)Creates new columns from existing ones (ratios, dates, interactions)Different, often better, columns — usually more of them at first
Dimensionality Reduction (e.g. PCA)Combines many columns into fewer new onesFewer columns, but each is a blend — harder to interpret directly

These aren't competitors — a realistic pipeline often engineers new features first (Lecture 05), then selects among the enlarged set (today's lecture), keeping only what earns its place.

In [ 15 ]:
A Practical Question

How Many Features Is Enough?

There's no fixed number — but there is a fixed way to find out: treat the feature count itself as something to tune, the same way you'd tune any other hyperparameter.

Plot cross-validated performance against number of features kept (exactly what RFECV does internally) — performance typically rises, then plateaus, then sometimes falls as noise features get reintroduced. Pick the count at the plateau, not the peak of a single noisy run.

A useful bias when in doubt: prefer the simpler model with fewer features if performance is statistically indistinguishable from a larger set — it's cheaper, more robust to new data, and easier for a human to trust.

In [ 16 ]:
Making the Correct Way Easy

Feature Selection Belongs Inside the Pipeline

The safest way to guarantee Slide 12's "select after the split" rule is never accidentally broken: make the selector a step inside the same Pipeline as preprocessing and the model — exactly like ColumnTransformer was in Lectures 02's capstone recap.

Call cross_val_score or GridSearchCV on the whole pipeline, and every fold re-fits the selector fresh, on that fold's training data only — the leakage trap becomes structurally impossible instead of something you have to remember.
