The Problem, in Plain Words

One Split Is a Coin Flip

Imagine studying for an exam and only ever taking one practice test. Did you score 95% because you really know the material, or because that particular practice test happened to ask the ten questions you were best at? You genuinely can't tell from one test alone.

A single train_test_split has exactly this problem. Which rows randomly land in the test set changes the score you get — sometimes flatteringly, sometimes unfairly — and you have no way to know which happened from that one number alone.

The fix is the same as in real life: take several different practice tests, and look at the average and how much the scores varied — not just one score in isolation.

In [ 4 ]:
The Core Idea

Split Many Times, Average the Results

Cross-validation's entire idea in one sentence: instead of splitting the data into train/test once, split it several different ways, train and score a fresh model each time, then average.

CV score = average of k separate test scores

That's genuinely the whole formula, in words instead of symbols. No calculus, no matrix algebra — just "do the same honest evaluation several times, then average," the same instinct as taking several practice tests instead of trusting one.

What you get that a single split can't give you: not just one number, but a sense of how much that number might have varied by chance — which is often more useful than the number itself.

The Standard Method

K-Fold Cross-Validation

Cut the data into k equal-sized chunks ("folds"). Use one fold as the test set and the rest as training — then rotate, so every fold gets exactly one turn as the test set. Every row gets used for both training and testing, just never at the same time.

In [ 6 ]:
Walking Through It

What Actually Happens, Step by Step

  • 1. Shuffle the rows (usually), then cut them into k equal folds.
  • 2. Set fold 1 aside as the test set. Train a brand-new model on folds 2–k.
  • 3. Score that model on fold 1. Write the number down.
  • 4. Throw that model away completely. Set fold 2 aside instead, train fresh on the rest, score on fold 2.
  • 5. Repeat until every fold has had its turn as the test set — k models trained in total, k scores recorded.
  • 6. Report the average of the k scores as "the" cross-validated score, and the spread (standard deviation) alongside it.

Important detail people miss: a fresh model is trained from scratch on each iteration. Cross-validation never reuses a trained model across folds — that would defeat the entire point.

In [ 7 ]:
A Practical Choice

Choosing K: 5, or 10, or Something Else?

Larger k means bigger training folds each time (closer to using "all" the data), but more models to train and more compute time. Smaller k is faster, but each fold trains on noticeably less data.

kTraining folds seeTrade-off
k = 3~67% of the data each timeFast, but noisier estimate
k = 5~80% of the data each timeThe most common default — a good balance
k = 10~90% of the data each timeMore stable estimate, roughly 2x the compute of k=5

When in doubt, use k=5 or k=10. Both are well-tested defaults across the field — there's rarely a strong reason to reach for anything unusual unless your dataset is very small or very large.

In [ 8 ]:
The Extreme Case

Leave-One-Out Cross-Validation (LOOCV)

Push k all the way to the number of rows in your dataset. Each "fold" is a single row: train on every other row, test on that one row, repeat for every single row in the dataset.

Upside

Uses the absolute maximum amount of training data on every iteration — as close to "train on everything" as cross-validation can get.

Downside

With 10,000 rows, that's 10,000 models trained. For anything but small datasets, this is usually too expensive to be practical.

Rule of thumb: LOOCV is worth considering on genuinely small datasets (a few hundred rows or fewer) where every data point is precious. Otherwise, k=5 or k=10 gets you nearly the same reliability for a fraction of the compute.

In [ 9 ]:
A Fix for Imbalanced Targets

Stratified K-Fold: Keeping Class Balance Fair

Recall the churn capstone: roughly 20-25% of customers churned. With plain K-Fold, pure bad luck in the shuffle could put far more (or far fewer) churners in one particular fold than in the others — that fold's score would reflect an easier or harder problem than the rest, purely by chance.

StratifiedKFold fixes this directly: every fold is built to contain the same proportion of each class as the full dataset. If churn is 22% overall, every fold's test set is (as close as possible to) 22% churned too.

Default choice for classification, always -- there's essentially no downside to stratifying, and a real risk of misleading fold scores without it, especially on imbalanced targets.

In [ 10 ]:
A Case Where Shuffling Breaks Everything

Cross-Validation for Time Series

Standard K-Fold shuffles rows randomly before splitting. For time-ordered data — sales by day, sensor readings, stock prices — that shuffle quietly lets the model train on the future and test on the past. It's a leakage problem, dressed up as cross-validation.

TimeSeriesSplit respects order: fold 1 trains on the earliest chunk and tests on the chunk right after it; fold 2 trains on everything up to that point and tests on the next chunk; and so on. Training data only ever comes before the test data in time, never after.

If your data has a time axis at all, ask this question before picking a CV strategy: would knowing "the future" here be cheating? If yes, plain K-Fold is the wrong tool no matter how well it scores.

In [ 11 ]:
A Common Misunderstanding

Cross-Validation Doesn't Replace the Test Set

Cross-validation happens entirely inside the training data -- it's a more reliable way to compare and tune models using only data you're allowed to touch during development. The held-out test set from Lecture 01 still exists, untouched, for the very end.

Three-way mental model: use cross-validation on the training data to choose a model and its settings; use the test set exactly once, at the very end, to report how that final choice performs on data it has never influenced in any way.

In [ 12 ]:
Use #1

Comparing Models Honestly

Recall the churn capstone and the Linear Regression lecture both comparing several candidate algorithms with cross_val_score. That's the single most common real-world use of cross-validation: deciding, with actual evidence, which algorithm deserves to move forward.

The one rule that makes the comparison fair: every candidate model must be scored on the exact same folds. Comparing Model A's 5-fold average to Model B's different 5-fold average is comparing noise, not comparing models -- reuse one cv object for every candidate.

In [ 13 ]:
Use #2

Tuning Hyperparameters

GridSearchCV and RandomizedSearchCV -- both already used in earlier lectures -- are really "try many hyperparameter settings, cross-validate each one, keep the best" wrapped in a single object. Today's lecture is what was happening inside that cv= argument the whole time.

GridSearchCV

Tries every combination in a grid you specify -- thorough, but the combinations multiply fast.

RandomizedSearchCV

Samples a fixed number of random combinations instead -- usually nearly as good, for a fraction of the compute on large search spaces.

Feature Selection's RFECV is the same pattern again: "how many features to keep" is just another hyperparameter, chosen by cross-validated performance instead of a guess.

In [ 14 ]:
The Trap That Catches Almost Everyone Once

Nested Cross-Validation

If you use cross-validation to tune a hyperparameter, and then report that same cross-validated score as your model's expected performance, you've quietly let the data pick its own grade -- the tuning process searched many settings specifically to find whichever one scored best on those folds.

The fix: two loops, not one. An inner loop tunes hyperparameters (that's what GridSearchCV already does internally). An outer loop then evaluates the whole tuning process -- including the search itself -- on data the inner loop never touched.

In scikit-learn, this is simply: cross_val_score(GridSearchCV(...), X, y, cv=outer_cv) -- a GridSearchCV (which already cross-validates internally) dropped inside another layer of cross-validation. The notebook demonstrates the gap between the honest and the optimistic number directly.

In [ 15 ]:
One More Look at an Old Problem

Cross-Validation and the Leakage Trap, Revisited

Feature Selection's leakage demonstration showed pure noise scoring an inflated R² when features were selected on the full dataset before cross-validating. The general version of that rule: anything that learns from data -- scaling, imputing, selecting features, encoding categories -- must be refit inside every fold, using only that fold's training data.

The dependable fix, every time: put every data-dependent step inside one Pipeline, and cross-validate the whole pipeline as a single object. Then there's no separate step to accidentally leave outside the loop.

In [ 16 ]:
Reading the Output

Mean and Spread, Read Together

cross_val_score returns k separate numbers, not one. Reporting only their average throws away real information.

Small spread (low std)

The model performs consistently across every fold — a trustworthy, stable estimate of real-world performance.

Large spread (high std)

Performance depends heavily on which rows happen to be in the training set — a sign the model (or the dataset) is unstable, and the mean alone is less trustworthy.

When comparing two models, a small difference in mean score with large, overlapping spreads is often not a meaningful difference — it may just be noise. The notebook shows this concretely with real numbers.

In [ 17 ]:
The Honest Trade-off

Cross-Validation Isn't Free

k-fold cross-validation means training k separate models instead of one. Wrap that inside a hyperparameter search over 20 combinations, and you're training 20 × k models. Nest that inside an outer loop for honest evaluation, and multiply again.

Practical ways to manage the cost: use k=5 instead of k=10 or LOOCV for early experimentation; use RandomizedSearchCV instead of an exhaustive grid; and save the most expensive, most rigorous setup (nested CV, large k) for the final decision, not every experiment along the way.

In [ 18 ]:
A Checklist

Common Mistakes, Collected

  • Comparing models on different folds — always reuse one cv object across every candidate.
  • Fitting a scaler/selector/encoder before splitting — put every data-dependent step inside the Pipeline that gets cross-validated.
  • Shuffling time-ordered data — use TimeSeriesSplit, not plain KFold.
  • Ignoring class imbalance — use StratifiedKFold for classification by default.
  • Reporting a tuned CV score as the final performance estimate — that number is optimistic; use nested CV instead.
  • Reporting only the mean — the standard deviation across folds tells you how much to trust that mean.
